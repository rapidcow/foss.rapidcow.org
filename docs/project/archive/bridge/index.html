The archive-bridge collection

This is a first “project archive” effort I can put a name to. Originally I was just trying to import my Apple Notes drawings from the trivial notetaking app (dumbly named trivnote); I also wanted to import my drawings from Concepts, and Samsung eventually. Then I want to get metadata from Procreate and… wait you can actually decode GoodNotes?!

I realized that this is way more than just Apple Notes. And since the second most important format I cared about, Concepts, was not getting nearly as much attention as Apple Notes had been getting, I just merged them into the shared Java package namespace I had been using for both.

The canonical source code is at git+https://git.rapidcow.org/pub/project/apple-notes.git. Mirrors exist at GitLab, GitHub, GitCode, and Gitee. Not available on SourceHut or Codeberg since I’ve used AI for reverse-engineering and prototyping.

archive-bridge is written in Java 17 and will remain on Java 17 until Android considers supporting Java 21 or 25. The package namespace is org.rapidcow.archive.bridge, and source files under this namespace are always available under LGPL v3+ (with the exception of AI-generated prototypes, which are un-copyright-able and thus cannot be licensed.)

archive-bridge will also include basic applications on top of the bridge libraries; when they are created, they are will be licensed under GPL v3+ (with the same exception of AI code).

What makes for a good bridge?

A bridge is an adapter (dumb name; don’t judge me :x) for a file format for which there doesn’t exist a well-known, robust SDK. A bridge should be doable by me (that is, nothing complicated on the level of OOXML / Adobe); and it should be a relatively stable format that requires no negotiation with Internet services (that is, no live sync/polling.)

For it to be interesting, I will only bridge to formats as close to the original, native storage as possible. That means if you export the database as CSV, I will not parse the CSV! (But if it is a ZIP’d CSV file, I could consider… (I still think it is very doable to parse that without a dedicate library though >:c part of what makes it interesting to me is also domain-specific file formats for which there exists no Internet standard formats, like PNG and SGML.))

What makes for a bad bridge?

Twitter. First of all, I would personally banish something as tumultuous as social media itself to a separate namespace, like org.rapidcow.archive.socials; second, lots of data require negotiation (such as liked tweets), which is not an easy process. (Also, please don’t ask me to call it X; I would confuse it with my X11 window system.)

The same goes for Mastodon which, albeit open source, is still far too complex for me to keep up.

What does a bridge do?

It adorns data structure with semantics. Yep, that’s about it.

(I don’t have working examples of this, so you’ll just take my words for it. :x In a nutshell, it’s all you can expect from object-oriented programming….)
