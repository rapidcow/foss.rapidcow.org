what is siteconf?

In the interest of most people’s time (and attention, for something so utterly unattractive in the market of real SSGs and CMSes) I will keep one quick (and inaccurate) and one slow (but thorough) version.

The layman pitch (and un-pitch): siteconf is a static-site generator. it is:

  • fast: it is said to be an incremental generator, meaning the sources you touch only affect the components that depend on it. siteconf supports the conventional setup of templates, such as the perl Template Toolkit, the python Jinja2 (and possibly ruby slim and racket scribble, but i haven’t tested), so that when you update the template, all files get the new look!
  • predictable: the recipe siteconf follows is explicit and builds to the byte-exact identical file (provided that the source files are intact and the commands themselves are deterministic and side-effect free).
  • configurable: with the locate function that comes with -P web it is possible to create templates that refer to static assets (such as CSS) as an absolute location but resolve relatively to the page’s location. so migration from a whole domain to a Unix-y ~tilde subpath and/or file://-respecting sites are explicitly supported. :) (With a bit of patchwork you can have it conditionally strip the .html suffix when the -Osite_url schema is (refer to us as an example!))
  • lazy: soft manifest entries and dependencies allow you to build only a portion of your site without heavy media files.
  • all text and stateless: no stinky binary cache. what you see is ALL you get.
  • all yours! depending on the templating language you use down to the spacing between <div> tags — that means of course, an abysmal lack of branding. (any amount of branding would be wrong anyways for technical reasons I won’t elaborate here, but should become obvious if you spend some time thinking about how it works.)

Don’t get too excited though because:

  • you need to bring your own recipe: opt into Template Toolkit with -P web, but otherwise it is assumed you will bring your own.
    • adding to specify that if you decide to not use Template Toolkit, or anything perl for that matter, you need to patch the script to perform version checks yourself; do it in a different script in a language of your choice; or just accept that we can’t (and won’t) do it here. :(
  • you need to name every file and every rule: you need to name every file you want to make, and for each of them, the rule to make them. if things get too tedious you can (and should) generate these files, but siteconf provides no mechanism for build everything in this directory. i give you the choice, which also means the responsibility, to decide when and how to do it.
  • you (likely) need to assemble your own pipeline: if anything you make is any more complicated than ./configure && siteconf -g && make, you are expected to make your life easier by writing a wrapper script for it. (scripts are awesome though! if you just want to get something up and running though, consider real SSGs like Gatsby/Hugo/Jekyll (or as i have been told repeatedly by someone, Astra) or real CMSes like Wordpress.)
  • you (very likely) need a unix-like environment. I myself am not a Windows user; and while i have reasons to believe a lot of the things are broken on Windows, i prefer not to try fixing them any time soon. You may consider WSL.

The technical pitch: siteconf is a build script generator; a POSIX Makefile generator, specifically (though it also supports GNU Make for weird space-ful paths; and Ninja just because Claude can lol.) siteconf is a command like make and uses tar-style single-letter flags to switch between modes.

  • siteconf -i initializes a script named ./configure; it is typically done at the project root (though you could set -SA if it lives elsewhere).
  • ./configure then writes your configuration variables (such as -DA -DB -Da -Db -Dc -De -DF -DR) to MY/config.mk and options (such as -Obase_url -Osite_url) to MY/option.mk relative to the build directory.
  • siteconf -g then generates the build script based on these variables and options, follows them to the manifest (-DF, which defaults to MANIFEST) and the rulebook (-DR, which defaults to Makefile.in), then expands all variables and implicit prerequisites and writes a Makefile.

then you run make, and the site builds. that’s all!

a few more cool things that may not appeal to most people, but putting them here for the lack of a better section anyways:

  • out-of-tree build support: siteconf can work on read-only checkouts by passing a desired writable build directory as -DB to it.
  • foreign configure support: as mentioned before, -SA (at siteconf -i time) or -DA can point to an arbitrary alternative project root (it’s particularly handy if you just want to try out siteconf, or if you are prescribing build instructions for someone else’s project with sources lying about); similarly, -Sa -Da can point arbitrary source directories.
  • gettext support: there is a Chinese (simplified) translation as a proof of concept, albeit with AI artifacts.
  • Unicode support: since version 0.03 siteconf is locale-aware. this version reeks of AI stink to this day, so don’t get too excited.
  • protection against directory traversal: the classic Unix shell horror of ${nonexistent}/etc/passwd does not work here since variable substitutions on full path segments are specially treated as path concatenation (calls uproot with an empty file segment, to be exact.) upward relative paths (i.e. consecutive runs of ../) are allowed but only when they are written as that literally in Makefile.in or it is explicitly configured via -Dvar (or a default); so ${root}/../secret.txt (or anything clever that expands to it like ${root}/${A}${A}/secret.txt) will never escape ${root}). provided that you review the Makefile.in carefully for any explicitly named absolute/relative paths and set -D on the directories you are okay with being read, siteconf should not read anything beyond that.
  • dependency headers for all! siteconf (GenGenLib) understands (and expects) a whole ton of programming language’s comment characters. (for you see, I am a fan of programming languages… ;.)

www-cellar borrows concepts from the cooper-www project/experiment, which similarly had a configure file, but lacked a way to modify the dependency graph without modifying the source code. It was GNU automake’s Makefile.am that inspired Makefile.in, and FreeBSD’s rcorder(8) header that inspired dependency headers for www-cellar. (The ${.TARGET} variable comes from Berkeley make, which is a modern re-spelling of the variable $@ from the original Make written by Stuart Feldman at Bell Labs.)

sub quote_sh {
	my @ret = map { s/'/'"'"'/; "'$_'" } @_;
	wantarray ? @ret : $ret[0];

sub map_src { my $name = shift; "src/$name" }
sub map_pub { my $name = shift; "public/static/$name" }

sub updir {
	my $path = shift;
	my $rpos = length $path;
	my $lpos = $rpos;
	while (($lpos = rindex ($path, '/', $lpos)) != -1) {
		last if $rpos - $lpos > 1;
		$rpos = $lpos;
		$lpos = $lpos - 1;
	}
	return if $lpos < 0;
	substr ($path, 0, $lpos);
}

This could not be more obvious but this, in turn, was inspired by EU::MM’s WriteMakefile.

I would like also to emphasize that cooper-www was not just an experiment for siteconf; it gave birth to ideas such as relative path computation in GenLib.pm (which can be used independently of SiteConf.pm).

None of the code in the cooper-www nor the www-cellar prototype was AI-generated; but then again, none of them were written exclusively during the hackathon either. (: On the other hand, siteconf was almost entirely AI-generated, but the ideas behind it were human, and arose from my experiments, BSD Make, rcorder(8) headers, GNU autoconf and automake, and the original Unix Make. Now while I do not find it unreasonable for this to be disqualified from the hackathon, I would also like to argue that building things from old pieces is the norm, not the exception. A good idea takes a while to develop; and a good abstraction comes from tried uses. There is something I don’t understand about the appeal of the ephemeral nature of hackathons that frankly, I may never understand. But to me, good things take a while to develop and take shape, and often take inspiration from great designs in the past. In that respect I cannot possibly claim siteconf to be this one thing I brainstormed and came up with this afternoon; but rather it was shaped from my needs for flexibly, predictably, and deterministically building my web sites over the three years I have been trying to make one; and it’d be simply distasteful to apply myself to fitness for an award for the feign originality, for I could not bear the remorse I would otherwise feel for leaving out the Unix/GNU/BSD predecessors that inspired me and claiming them all as my own.

about names

It's obvious enough where configure and Makefile.in come from and, to a lesser extent, where MY came from (it is EU::MM and perl, I will tell you that.) siteconf is genuinely a new name that, I can’t quite recall where but, it was perhaps GPT web when I typed my desire to separate the generation step from the configure step, then when it meant a whole rewrite I wanted to rewrite it for good so I asked in frustration for the lack of a good name. GPT suggested siteconf, possibly as a concatenation of the site/ directory of www-cellar, and shortening of conf as seen in autoconf(1). Then the rest is history….
